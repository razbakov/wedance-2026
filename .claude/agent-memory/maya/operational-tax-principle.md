# Operational Tax Principle — Universal Rule for 2-Person Team

last_updated: 2026-04-07
applies_to: ALL agents, ALL recommendations, ALL systems
version: 2 (founder-calibrated)

## Core Truth

SDTV = 2 people + 2 outsource contractors. No sales manager, no ops manager, no project coordinator.
Every system, field, process, tool has a hidden cost: ATTENTION.
Attention is the scarcest resource. Everything competes for it.

**BUT: the goal is NOT "make everything as light as possible."**
The goal is: **достаточно лёгкая для двоих, достаточно сильная чтобы усиливать бизнес, а не только снижать хаос.**

CRM is not bureaucracy for order. CRM is not a convenient task list.
CRM must hold control over money, promises, next steps, and future revenue.

## The 4-Filter Test

Before recommending ANY new field, process, tool, automation, or workflow — check ALL FOUR:

### 1. CONTROL — даёт ли реальный контроль?
Помогает понять что происходит по клиенту, проекту, фестивалю — без опоры на память и переписки.

### 2. SPEED — ускоряет ли действия?
Помогает быстрее принять решение, увидеть next step, не потерять дедлайн или follow-up.

### 3. COMMERCIAL MEMORY — сохраняет ли коммерческую ценность?
Помогает не потерять: деньги, renewal, upsell, sold vs delivered, margin, promo value, следующий цикл с клиентом.

### 4. REALISTIC — реалистично ли поддерживать?
Будут ли два человека реально это вести в рабочем ритме, особенно в фестивальные недели, а не только в идеальной модели.

## Decision Logic

| Control | Commercial Memory | Realistic | Decision |
|---------|-------------------|-----------|----------|
| No | No | — | **Remove** — слабый, почти точно лишний |
| Yes | Yes | No | **Don't remove — find lighter implementation** |
| — | No | Yes | **Remove** — лёгкий но бесполезный, даже если почти ничего не стоит |
| Yes | Yes | Yes | **Keep** — это рычаг |

**Ключевое правило:** если элемент даёт контроль и сохраняет коммерческую ценность, но тяжёлый — НЕ выбрасывать. Искать более лёгкую реализацию.

## Commercial Memory — What It Protects

These things don't look "light" but have high value because they preserve business context that otherwise vanishes:

- Что именно было продано
- Что уже доставлено
- Что ещё обещано
- Где окно renewal
- Какой следующий коммерческий шаг
- Где есть upsell opportunity
- Какой тип пакета у клиента
- Есть ли promo component
- Насколько проект был маржинален
- Как этот клиент монетизируется в следующем цикле

Some of these cost 30 seconds to update but save a lost renewal, forgotten upsell, or confusion about what was actually sold. For SDTV this is revenue protection, not administrative detail.

## Useful vs Harmful Load

### Useful load (KEEP — saves more than it costs):
- Record next step
- Mark what's sold vs delivered vs promised
- Hold delivery deadlines
- Track renewal windows
- See where money and risk are
- Capture upsell / next-cycle opportunities
- Record margin per project

### Harmful load (KILL — costs more than it saves):
- Same info in 3 places
- Fields "just in case"
- Statuses nobody updates
- Manual actions without which system breaks
- Complexity that gives neither decisions, money, nor control
- Light but commercially useless fields

## Agent Behavior Rules

### Core principle for ALL agent recommendations:
NOT "make lighter at any cost"
BUT "make light enough to actually maintain, strong enough to hold commercial logic"

### When recommending new fields/processes:
- Run all 4 filters, not just "is it light?"
- If it protects revenue (renewal, upsell, margin, sold-vs-delivered) — find a way to keep it, even if it costs a little effort
- If it's light but doesn't serve control, speed, or commercial memory — skip it anyway

### When something is valuable but heavy:
- Don't remove it. Ask: "Can we make this lighter?"
- Automation that fills the field automatically = ideal
- Dropdown instead of free text = lighter
- Default value that only changes on exception = lighter
- Linked field that auto-populates = lighter

### When reviewing existing systems:
- Don't praise structure — ask "does it help or tax?"
- Look for: duplication, dead fields, statuses that drift, manual glue
- If information lives in Telegram/WhatsApp instead of Monday → signal (Monday too heavy or missing something critical)
- If commercial context is missing from Monday → that's a gap, not a feature

### When building automations:
- Best automation: one that means founder touches FEWER fields, not more
- Automation that protects commercial memory without manual effort = highest value
- Automation that adds complexity without removing load = harmful

## The Real Test (post-festival)

1. Without this board, would it have been significantly harder?
2. Did it help make at least 3 important decisions during the project?
3. Did it help NOT forget at least 2 important actions?
4. Did updating take reasonable time?
5. After the festival, is it clear what was sold, delivered, and what's next?
6. Is there enough context for renewal / upsell without re-researching?

Majority YES = system works.
Majority NO = still decorative.

## Quick Check for Any CRM Element

- Record/update takes < 1-2 minutes? ✓
- Next step visible immediately? ✓
- Same info not written twice? ✓
- Weekly review passes quickly? ✓
- After 3-4 day pause, can open board and instantly understand context? ✓
- Commercial context preserved for next cycle? ✓

If any ✗ → investigate. If fixable by lighter implementation → fix. If not → remove.

## The Formula

## Operating Standard (final, founder-approved)

Не оптимизируем систему только под простоту.
Оптимизируем систему под управляемость бизнеса в маленькой команде:
**достаточно лёгкая чтобы реально вестись в нагрузке, достаточно сильная чтобы удерживать контроль, коммерческую память и будущую выручку.**

### Compression Rule

**Если элемент защищает деньги или decision quality, но слишком тяжёлый — задача не "убрать", а "сжать до минимальной рабочей формы".**
